DAWN OF DECAY — THE CLASS MERGE RECONNAISSANCE

What it would cost to dissolve the twelve specs into their four classes, derived from the code. This is a REPORT. Nothing was authored, merged, changed, retired or retuned — no spec was collapsed, no engine was moved, no node was cut, no rune was re-scoped, no card changed pool, no constant and no magnitude moved. Every section below is written to be read ALONE, because this document will be opened many times across many batches and never once from the top.

THE PROPOSAL THIS MEASURES. The twelve specs dissolve into their four classes. Each spec's passive becomes an ENGINE RUNE and its enabler travels with it; a hero is guaranteed one engine rune early. The three spec draft pools of a class merge into one class pool, and the three rune pools with them. Each class gets one CORE ENGINE every hero of that class holds — Focus for the Hunter (it exists), and three that do not: MOMENTUM (Warrior), CHANNEL (Mage), SANCTITY (Cleric). The twelve talent trees merge into four with no lanes, under a new rule: NO NODE MAY DEPEND ON AN ENGINE.

§1b — THE FINDING THE BRIEF DOES NOT ANTICIPATE: SPEC_INFO IS A STAT BLOCK

A SPEC IS NOT ONLY AN ENGINE AND A POOL. IT IS A BODY. Every one of the twelve declares max_hp, armor and constitution; eleven declare resists; and two declare a defensive stat that exists nowhere else.

THE WARRIOR SPANS 35 MAXIMUM HEALTH AND MORE THAN DOUBLE THE ARMOR, so a merged Warrior needs ONE stat line and choosing it is a design decision with a survivability cliff under it — not a bookkeeping step.

AND ONE OF THOSE TWO ODD STATS IS LOAD-BEARING FOR A WHOLE LANE. parry_chance defaults to −1.0, a sentinel meaning “use the role baseline”, and PARRY_CHANCE := 0.05 is that baseline for every hero — so parry is universal and the Swordmaster's 0.12 is an override. block_chance has no baseline at all. It defaults to 0.0 and is declared by exactly one spec. A hero's live Block is block_chance + _plating_slice(u), and _plating_slice opens (0.15 + u.plating_bonus) if u.passive_id == "heavy_plating" else 0.0. So Block has two unconditional sources in the entire game and the Warden owns both — his stat block and his passive. An engine rune carrying Heavy Plating to a Berserker would install a climb on a base of zero, and PROTECTED_CORES cannot see it, because the enabler table names ABILITIES and this is a STAT. The Warden's enablers list is empty and that is the most misleading empty list in the merge.

§1c — THE RUN SAVE: TOLERANT, AND NOT THE PROBLEM

The run save is at v12 and refuses below v10. A hero's spec lives at party[i]["spec"], read at 15 sites in run_state.gd, plus specs_chosen, plus party[i]["tree"], which holds a copy of the spec's node array. Four versions of precedent say what to do here, and the precedent is consistent: BK refused pre-v8 and BM refused pre-v10, both because the migration would have to invent state the party never had; CT and EG both went TOLERANT because their new state had an honest default.

A CLASS MERGE HAS NO HONEST DEFAULT. A v12 party member holds a spec id, a spec tree and a loadout drafted out of a spec pool. Under the merge the spec id names nothing, the tree array holds ids the merged tree does not contain, and the pool the loadout came from is gone. The only faithful migration is v13 REFUSED — and refusing a run save costs one evening, which is what BK and BM both judged acceptable. The run save is not where the risk is.

§1d — Profile IS WHERE THE RISK IS, AND THE FAILURE MODE IS SILENCE

Seven of Profile's buckets are keyed by SPEC: runs_started, runs_completed, wipes, forfeits, and the three that are the meta progression — talent_points (points earned, ever), talent_cells (the permanent unlock ledger) and talent_equipped (the loadout). Only talent_tier is global.

Profile._load() HAS NO VERSION BRANCH. It builds the defaults, merges every key it finds in the file over them, and then writes data["version"] = VERSION unconditionally. Nothing reads the version it just overwrote. There is no refusal, no migration hook and no log. VERSION := 2's own comment says why that was right at the time: “Nothing migrates because nothing could.”

AND THE ARITHMETIC IS DERIVED, WHICH IS THE PROPERTY THAT TURNS A RENAME INTO A LEAK:

  talent_points_available(spec) = talent_points_earned(spec)
                                − Talents.cells_spent(tree, talent_cells(spec))

cells_spent walks the ledger and silently skips any id the tree does not hold (if not t.is_empty()). equipped_learned does the same. There is no second accounting anywhere — which is a virtue for a respec and a hole for a migration.

CONSTRUCTED AND DRIVEN, NOT INFERRED. A scratch profile was built with the tier at 3, six points awarded to the Berserker, three cells bought (bz_savagery, bz_hemorrhage, bz_crushing_blows) and one equipped. Against the real tree it reads earned 6, spent 3, available 3 — correct. The same ledger asked against a tree that no longer holds those ids returns: cells_spent 0 · equipped_learned { } · owns_cell still true for all three. So the points come back, the loadout empties, and the ledger still claims to own cells that now cost nothing. Nothing errors and nothing logs.

AND THE OTHER DIRECTION IS WORSE, BECAUSE IT IS INVISIBLE RATHER THAN WRONG. Talents.has_tree("warrior") is false today and generate_tree("warrior") returns 0 nodes — class keys have no tree. If the merge keys the new trees by class and leaves the profile alone, the build screen enumerates four classes at zero points while twelve spec purses sit in the file, un-migrated, indistinguishable from a profile that has never completed a run.

WHAT A MIGRATION HAS TO DO, AND THE ONE PART THAT IS A DESIGNER'S RULING RATHER THAN A PROGRAMMER'S:

  • Bump Profile.VERSION and give _load() the branch it has never had. This is the load-bearing line: without it, every later fix is a guess about which shape the file is in.
  • Fold twelve purses into four, and the RULE IS THE RULING. A player with 3 points on each of three Warrior specs has 9 spec-points. Does the Warrior get 9, or 3? Sum rewards the player who played all three; max rewards the player who mastered one. The trees also got three times shallower, so summing may hand a full tree on day one. This document does not choose.
  • Re-key or drop talent_cells. Ids that survive into the merged tree can be carried; ids that do not must be dropped explicitly, because leaving them costs their price and keeps their ownership.
  • Drop talent_equipped outright. It is row-keyed against a nine-row spec tree; a merged tree with no lanes has different rows. A stale row key equips nothing and says nothing.
  • The four chronicle buckets can be summed with no ruling — runs and wipes per class is a strictly weaker fact than per spec, and nothing gates on them.

WHAT IS UNRECOVERABLE IF IT IS GOT WRONG: _save() writes the merged dictionary back over the file on the next point earned. So a bad first load is not a bad read — it is a bad WRITE, and the original spec purses are gone the first time the player beats a zone boss. There is one backup and it is the player's own filesystem. Whatever else this project stages, the profile migration is written once and cannot be iterated on live.

§1f — THE BOT SURVIVES, AND THAT IS THE ONE PIECE OF GOOD NEWS IN §1

_autoplay_pick_kit is 645 lines (battle.gd:4543–5187) and holds ZERO spec-id literals. It branches on passive_id exactly four times — bloodrage, seasoned, heavy_plating, permafrost — and everything else it does is name-keyed: it fetches an ability, tests ab != null and a resource, and picks. That is already the question the merge asks (does this hero happen to hold this card?) rather than the question it removes (is this hero this spec?). _focus_mark is one guard on passive_id != "lethal_aim" and re-points identically.

SO THE BOT NEEDS FOUR BRANCHES RE-POINTED AND NOTHING ELSE, and the reason is a decision somebody already took: the heuristics were written against what a hero has, not against what a hero is.

Focus alone names a targeting DISCIPLINE and pays a UNIVERSAL stat. It is the only one of the twelve whose two halves are both build-blind.

§2b — WHAT THE THREE NEW SPINES NEED, AND WHICH IS CHEAPEST

THE ANSWER, RANKED, BEFORE THE WORKING.
CHANNEL is cheapest by a wide margin — the reading door exists and is already generic in shape, and the payout is one line that already exists.
MOMENTUM is middling — half the reading exists with worked-out semantics, the other half must be built to a shape the file already uses twice; the payout is small but touches the one function every turn passes through.
SANCTITY is dearest, and it is not close. Its reading half is the cheapest of the three. Its payout half does not exist anywhere in the game.

CHANNEL — reads Mana spent, pays spell damage. CHEAPEST.

THE READING DOOR IS ALREADY BUILT AND IS ALREADY GENERIC. BattleUnit.note_resource_spent(amount) takes a plain integer, and its four call sites are resource-blind. The load-bearing one is battle.gd:8015, and its own comment states the property Channel needs:

  var cz_res_before: int = attacker.resource
  attacker.resource = clampi(attacker.resource - _eff_cost(...) + ab.resource_gain, 0, ...)
  attacker.note_resource_spent(cz_res_before - attacker.resource)

“This one line is where every ability in the game pays, so measuring the difference catches the waivers, the discounts, the refunds and the clamp at zero without knowing any of their names. It books the NET, so a card that hands back what it took feeds the band nothing.” That is un-farmable Mana-spent for free.

WHAT IS ACTUALLY MISSING IS TWO LINES. The function opens if amount <= 0 or resource_name != "Rage": return and writes rage_spent. A Mana equivalent needs the guard widened and a second field — and EM's charter forces the second field rather than a shared one, because rage_spent holding Mana is a name that lies (the exact objection FO §1 raised against rune_hex_threshold).

AND THE PAYOUT ALREADY EXISTS AS ONE LINE. battle.gd:9770 is the entire general damage multiplier in the game:

  raw *= 1.0 + attacker.dmg_bonus + float(attacker.type_dmg_bonus.get(ab.dmg_type, 0.0))

dmg_bonus is read at exactly one site and is element-blind by construction, which is what the brief asks Channel to be. “Spell damage” as distinct from all damage is the one open question: there is no is_spell flag on Ability. The available partition is dmg_type — arcane / nature / shadow / holy / physical / fire / frost — so spell would have to mean not physical, or Channel pays into dmg_bonus and buys the basic attack too. That is a ruling, not machinery.

MOMENTUM — reads damage dealt AND taken this turn, pays initiative. MIDDLING.

THE TAKEN HALF EXISTS TWICE OVER, WITH ITS SEMANTICS ALREADY ARGUED OUT.

  • dmg_by_turn — damage taken keyed on the global battle_turn, written by _report_taken (“the one door, so it books what was ACTUALLY removed, below every death refusal”) and bounded to two keys so a 90-round stalemate cannot grow it.
  • trance_taken — damage taken since his last turn, and its comment says exactly why it is not a read of the other one: “that one is a fixed two-turn window keyed on the GLOBAL turn index, this one is the span between one hero's turns.” Momentum wants the second shape, and it is already built.

THE DEALT HALF DOES NOT EXIST. What exists is total_dealt, a local inside _resolve() alive for one cast, and _run_dealt, a run-long hero→ability recap ledger. Neither is a per-turn count. But the shape to copy is unambiguous: heal_by_turn is described in its own comment as “the exact mirror of dmg_by_turn”, bounded the same way and written at one door. A dealt_by_turn would be the third of the same shape, and the file already tells you where to put it.

THE PAYOUT IS THE PART THAT NEEDS A DECISION. effective_speed() is one function with a closed list of six terms — speed, mod_speed_mult, Slowed, Chilled, Quickdraw, Wrath — and five of the six are statuses or a run modifier. There is no general per-unit speed multiplier a passive could feed: mod_speed_mult belongs to the Frenzied modifier. So Momentum pays initiative one of two ways, and they are not equivalent:

  • A seventh term in effective_speed() — one line, but it is the function all 23 next_time writes divide by, so it bends the timeline continuously and every existing speed interaction compounds with it.
  • A next_time write at a chosen moment — Shockwave's and delay_push's shape, discrete and legible, and it does not compound.

The brief's instinct is right that _bond_convert is the precedent: a one-line body, one place deciding one thing, with check_eu §0 asserting that a second naming of the constant takes the gate red. Initiative IS writable. What does not exist is a place to write it that belongs to a passive.

SANCTITY — reads statuses applied or removed, pays potency and duration. DEAREST, AND THE PAYOUT IS THE REASON.

THE READING HALF IS THE CHEAPEST OF ALL THREE, WHICH IS THE SURPRISE. BattleUnit.add_status() is the single funnel: _apply_status is called 214 times in battle.gd and calls add_status exactly once; 35 further sites call add_status directly. So every status application in the game — 249 call sites — passes through one function, and the brief's “from any source, on anyone” is answerable there in one line. Removal is the same shape: remove_status and purge_debuffs are called from 64 sites.

BUT “HE APPLIES” IS NOT ANSWERABLE AT THE FUNNEL, AND THAT IS WORTH KNOWING BEFORE THE WORDING IS SETTLED. add_status is a method on the TARGET and receives no source. _apply_status has an optional src defaulting to null, and of its 214 call sites, 110 pass a source and 104 do not — plus 35 direct add_status calls that have no source parameter at all. So the brief's broad reading is one line and a narrowed one is 139 call sites.

THE PAYOUT IS THE RISK AND THE BRIEF IS RIGHT TO SAY SO. DURATION HAS ONE GENERAL TERM POINTING THE WRONG WAY, AND POTENCY HAS NONE AT ALL.

  • DURATION. mod_status_turns is the one general term — an additive integer, read at exactly one site in add_status (turns = maxi(turns + mod_status_turns, 1)). It is read off the VICTIM, not off the applier, it belongs to the Fleeting run modifier, and it is only ever set to −1. Sanctity needs the applier's, which is a different read. Battle-long statuses carry a negative turn count as a permanence flag and are exempt, so any duration multiplier inherits that exemption or breaks permanence.
  • POTENCY: THERE IS NOTHING. STATUS_INFO holds 156 status ids and carries label, short code, colour and description — and not one magnitude. Strength arrives as the per-call power and tick arguments (67 of 214 calls pass a non-zero power, 25 a non-zero tick) and everything else lives in the handler that reads the status. Every status magnitude in this game is authored per site. That is the finding.

SO SANCTITY'S PAYOUT IS NOT A CONSTANT TO ADD — IT IS A LAYER TO INVENT, and it has to be invented across 156 statuses whose numbers are currently written wherever they are used. And there is a shape in the file that says how hard that is: _status_write_improves already had to normalise Fleeting by hand to compare two writes, and its comment explains why — because add_status applies the modifier after the caller has decided. A second general modifier doubles that problem at every site that compares two status writes.

§2c — WHAT A CLASS ACTUALLY SHARES TODAY, AND IT IS THINNER THAN IT LOOKS

A class-core engine has to sit on what all three specs are guaranteed. That is the class kit and nothing else.

  • THE CLASS KIT IS SHARED — but not intact. apply_kit_overrides replaces abilities[0] for four specs at spawn (Fireball, Frostbolt, Arcane Explosion and — DV §5's correction — the Occultist's Shadowrend), so a class's basic attack is not even the same card for all three of its specs. Three of the four Mage specs and one Cleric spec walk in with a different opening than kit("mage") / kit("cleric") describes.
  • THE CLASS-WIDE DRAFT CARDS ARE NOT GUARANTEED AND ARE NOT THREE. Premise 12: the pools are 6 / 7 / 6 / 6 and CLASS_DRAFT_SHARE is 0.25 per card, deliberately — “so a three-card offer averages 0.75 class-wide entries rather than being forced to hold exactly one.” A hero can finish a run having been offered none.
  • THE CLASS RESOURCE IS SHARED AND IS THE REAL FLOOR. All three Warriors use Rage (verified at the site), the Mages Mana. This is why Channel's reading half is legitimate as a class core and why Momentum's is too — both read something every hero of the class has by construction.
  • AND THE STAT LINE IS NOT SHARED AT ALL — §1b. The Warrior spans 165–200 max health and 0.15–0.32 armor, and two of its three specs own a defensive stat the others do not.

SO THE HONEST FLOOR A CLASS CORE MAY STAND ON IS: the class resource, the class kit minus its overridden basic, and the universal systems in §3b. Not the class draft pool, and not the stat block.

§5b — WHAT CANNOT BE STAGED

  • THE ENGINE MOVE CANNOT BE STAGED PER SPEC, AND THIS IS THE STRUCTURAL ANSWER TO THE BRIEF'S QUESTION. The unit of the merge is a class: three specs collapse into one pool, one tree and one stat line simultaneously or the pool holds a spec that no longer exists. And the tree is shared — there is no state in which the Berserker has merged and the Warden has not, because they would need one tree and two. The smallest shippable step is a whole class, and a whole class is batches 3–6 for one quarter of the game.
  • THE PROFILE MIGRATION IS WRITTEN ONCE. §1d: _save() overwrites the file on the next point earned, so a wrong first load destroys the original purses. It is staged early and it is not iterated.
  • THE THREE NEW SPINES CAN BE STAGED AND SHOULD BE. They are additive machinery on nobody, and Sanctity's potency layer is the same thing §3c says the merged tree needs — so batch 2 pays for itself twice whether or not the merge ever happens. It is the one piece of this project worth building on its own.
  • THE BATTERY CANNOT BE STAGED AHEAD OF THE CODE. A band-3 target has to be told how to GET an engine, and that mechanism does not exist until batch 3. So the instruments go red first and are repaired after — which inverts the order this project has always worked in.

§5c — WHAT I WOULD THROW AWAY

DN'S SENTENCE WAS “THE COST IS NOT IN THE 324. IT IS IN THE 97”, AND THE DESIGNER DID NOT TAKE IT. THE EQUIVALENT SENTENCE IS THIS:

THE MERGE THROWS AWAY 274 TALENT NODES, 43 RUNES AND 83 DRAFT CARDS — AND IT THROWS THEM AWAY TO BUY A CHOICE THE PLAYER ALREADY MAKES.

The talent layer is 324 purpose-authored nodes and 50 survive. The rune layer is 60 runes finished four batches ago and 43 become conditional on a draw. The draft is 154 of 154 complete and 83 read an engine the drawing hero may not hold. That is 274 + 43 + 83 = 400 authored things that stop meaning what they mean today, against a spec system where a player already chooses one of three identities per class — the merge moves that choice from the spec-select screen to the draft, and charges 400 pieces of content for the move.

AND THE PART THAT IS NOT RECOVERABLE BY WORKING HARDER: four specs contribute ZERO surviving nodes. Pyromancer, Cryomancer, Holy and Beastmaster are 108 nodes and not one of them says anything to a hero who did not draw their engine. Those four trees are not re-pointed. They are deleted and replaced.

SO IF ANY PART OF IT IS TAKEN, TAKE THE PART THAT COSTS NOTHING TO REVERSE, AND IT IS BATCH 2. Momentum, Channel and Sanctity as machinery on nobody. Channel is two lines and one ruling (§2b). Momentum is one ledger in a shape the file already uses twice, plus a decision about where initiative is written. Sanctity's potency layer is the single largest unbuilt system this recon found, and §3c wants it independently — the merged tree needs it, and so does any future batch that wants a status to be worth more to one hero than to another. Build them, and the merge stays possible without any of the 400 pieces being touched yet.
