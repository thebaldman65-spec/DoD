# Batch JV — The composer picks without listing

**THE DECISION RECORD IS WELL FORMED, AND ONE PREMISE IT QUOTES DID NOT HOLD, SAID HERE FIRST**: its first section quotes JU §3 — a composer that picks without listing *would move every seeded fight* — and the quote is JU's, but the claim is not true of the draw this batch built. `pick_random()` is `arr[randi() % arr.size()]` and spends one die (JV's probe on Godot 4.7), so a draw that counts the list and takes `randi() % count` returns the warband the list held at that index: **every seed draws what it drew before, and no seeded fight moved** — the probes hashed 200 seeds of every caller and 40 whole maps equal on both codes, `check_jv` §2 holds it every battery, and the recon read every seeded row unmoved. **LANE A RAN — THE WHOLE FLOOR**, as the record declared.

**THE VERDICT: DONE — GREEN BUT FOR THE TWO CARRIED REDS.** **The composer draws without listing**: `compose`, `compose_test` and `compose_budget` call `Run._theme_pick`, which counts the warbands a theme could field at a budget — memoised on what the leaf test reads — and walks to the one the die names; `_theme_combos` stays as the door two gates derive through. **A Forest map's fight and elite draws take 51 ms where HEAD's took 819**, a whole map's generation 17 ms where it took 281, and `check_map`'s 1,500 zones 27.0 s where JU's pre-run read 141.3. **With six kinds more in roster 1 the draw slows ×1.45 (51 → 74 ms) where HEAD's list slowed ×5.2 (819 → 4,294 ms)**: a roster's kind count no longer sets what a map costs — it still nudges it, a little faster than the kinds grow (×1.45 for ×1.30), and that is stated, not widened. **JT's four rulings still owed and JU's six are accepted as taken and archived; the Lane B floor gains its recon clause; the record gains two habits.** This report ends with what JW's decision record owes.

**THE WORDS THIS REPORT USES.** *The record*: JV's decision record (`RECORD_JV.md`, as handed over). *The list*: `Run._theme_combos`, every warband a theme can field that spends a budget exactly, in its walk's order. *The draw*: `Run._theme_pick` and the functions under it, which count the list and find one warband in it without building it. *The same die*: one `randi()`, taken modulo the list's size, as `pick_random()` takes it. *A lane* means a batch's kind except where it says a lane folder. ## §1 — THE COMPOSER DRAWS WITHOUT LISTING

**THE ROUTE (Q1's first branch).** `scripts/run_state.gd`:
- **`_theme_pick(spec, budget, roster, named_boss)`** builds a frame (`_draw_frame`: each role's kinds with their power, weakness and mender tag, the pool's caps and floors, the leaf test's terms), counts the warbands (`_draw_total` → `_draw_count`), returns `[]` when there are none — spending no die, as an empty list spent none — and otherwise returns `_draw_unrank(dw, randi() % total)`.
- **`_draw_count`** counts the leaves the list's walk would reach from a state: the role and its kind, the role's slots left, the budget left, the units so far, the majority role's units, the weak units (capped at the theme's floor), the distinct kinds (capped at its floor) and the mender-tagged units — everything `_combo_ok` reads, the floors (`mins`) read as each role is left. **Memoised on that state, so its work grows with the states, not the warbands.**
- **`_draw_unrank`** walks the kinds in the walk's own order — at each, none of it, then one, then two — taking the branch whose count holds what is left of the index: **the i-th warband in the list's order**, never built beside the others.
- **`_role_kinds`** is the claims loop, moved out of `_theme_combos` so the list and the draw read one answer; **`_menders_ok`** is the mender ceiling, moved out of `_combo_ok` for the same reason (the draw stops a kind's branches at the first count past it). `_theme_count` and `_theme_at` serve the gate.
- **`compose`, `compose_test` and `compose_budget`** call `_theme_pick` where they called `_theme_combos` and `pick_random`; `last_theme` is set at the same moments; the plain-mob fallback is untouched. **`_theme_combos` stays** (Q2), its header saying no game path calls it.

**THREE CASES NO THEME OR DATA REACHES, NAMED RATHER THAN CODED** (the new text's reader): a list holding an empty warband (a theme with `min_units` 0 at a budget of 0 — HEAD's `compose` would have returned it, JV's tries the next theme); a negative pool cap or power, which would let two of the memo's packed keys collide; and a zone's named boss claimed by a role before the escort's `boss` role, which the draw would count as a second distinct kind. `check_jv` §1 reds the day any of them is reached on the data it walks.

**WHY THIS ROUTE.** The probe settled it before a line was written: `pick_random()` is `arr[randi() % arr.size()]` — 20,000 of 20,000 seed-and-size pairs up to 300,001 drew the same element and left the same next die (`probes/pick`, a bare probe; `logs/pick.txt`, its print kept at the close). So exactness needs no enumeration: count, then unrank at the die's index. A draw that spends a die at each choice would draw from the same odds and re-roll every seeded row; this one re-rolls none, and that is a property of the code, not a preservation (JV's ruling 1).

**THE PROOF, IN THREE PARTS.**
- **The draw is the list**: every roster 1–5, every theme, budgets 1–14 and the Boss Escort with each zone boss named and with none — **1,050 lists, 235,519 warbands, the count equal to the list's size and the i-th found equal to the list's i-th, every one** (`probe_jv_equiv.gd`; `check_jv` §1 every battery). JU's own hash text, built from the draw, reads the list's md5, `f2571201…` (209,671 warbands; premise 9).
- **The dice**: 200 seeds of `compose` on every node type, `compose_test` on every theme and roster and `compose_budget` on every roster, each followed by the next die, and 40 whole maps through `_generate_map` — **md5 `b0c67a94…` and `be6daeb2…` on HEAD's code and on JV's** (`probe_jv_dice.gd`, 195 s on HEAD, 13 s on JV). `check_jv` §2 emulates HEAD's `compose` — the list, `pick_random`, the shuffle — beside the game's, seed for seed.
